# Current Security Audit (Sprint 0.22)

## Implemented foundation

- Laravel Sanctum is installed; users use `HasApiTokens`, password hashing casts, and hidden password/remember-token fields. Browser API requests from configured stateful origins use Sanctum's cookie/session and CSRF flow; mobile uses Bearer PAT semantics. No server login/logout/token issuance route exists yet.
- Tenant middleware resolves an organization, requires an authenticated user with an **active** membership, establishes context, and clears it in `finally`. Health is public and tenant middleware remains explicit; stateful middleware alone never authorizes a tenant.
- Credentialed CORS is implemented with `CORS_ALLOWED_ORIGINS`: local explicit origins in `.env.example`, explicit deployment configuration for production, and no wildcard. Session cookies are HTTP-only, `SameSite=lax`, environment-controlled for `Secure`, and have a 120-minute configured lifetime. Session regeneration is a requirement for the future login endpoint.
- API exception handling suppresses internal error detail in production. CSRF remains enabled; no implemented API route disables it. No domain write, raw SQL, file upload, or business module endpoint exists.
- Mass-assignment audit: `User` guards ID, organization, role, and active status; `Organization` guards ID; `OrganizationMembership` exposes no fillable fields; `Branch` guards ID and organization. No `$guarded = []`, `request()->all()`, or request-array `create`/`update` usage was found. Test setup uses explicit `forceFill` for server-controlled membership fixtures.
- No web authentication/token storage is implemented. The sole generic `useLocalStorage` hook is unused by auth and classified as a non-sensitive preference utility. No `sessionStorage` or `dangerouslySetInnerHTML` use was found.
- Mobile auth tokens now use `flutter_secure_storage`; SharedPreferences holds only non-secret metadata. Dio adds a Bearer header from secure storage but debug logs only method/path/status. The sync prototype restricts queued entity/operation names to its fixed supported set instead of accepting arbitrary endpoint/table names. The current SQLite database is plaintext and holds sensitive organization/user/offline queue data.
- Desktop has no credential, HTTP, or local database implementation. It configures console/debug logging but has no sensitive log statement. Future token storage remains Windows Credential Manager/DPAPI.
- Repository secret-pattern scanning found environment templates, local-development placeholders, framework field names, documentation/examples, and a test password only. No PEM/private-key marker or production credential was found. Tracked `.env.example` values are classified as local/example data, never deployable secrets.
- API security tests cover public health, configured credentialed CORS, active/unauthenticated/inactive membership behavior, cross-organization denial, downstream-exception tenant cleanup, Sanctum stateful middleware configuration, and mass-assignment protection (18 tests / 50 assertions in the final run).

## Framework upgrade re-run (2026-10-20)

This section supersedes the dependency details above where they differ. The recorded Laravel 10 and Next 14 security debt has been resolved through the deliberately tested migration recorded in [ADR 0031](../adr/0031-framework-version-upgrade.md).

`composer audit` reports **no security vulnerability advisories** for Laravel 12.70.0 with Sanctum 4.3.3 and spatie/laravel-multitenancy 4.2.1. The four previously reported `laravel/framework` advisories (PKSA-d5tc-s1qs-h781, PKSA-m5cs-t1y6-qpcs, PKSA-3r5d-mb8f-1qw9, PKSA-mdq4-51ck-6kdq) have no compatible patched Laravel 10 release and are all fixed by the Laravel 12 line.

`npm audit --omit=dev` reports **0 vulnerabilities** for the production dependency tree on Next.js 15.5.28 with React 19. The previously reported critical Next advisories GHSA-p293-qw3h-jr36 and GHSA-2xp9-vwfh-vxw4 affect versions below 15.5.24 and are fixed by this line, and no other Next advisory applies to the installed version.

Next 15.5.28 still pins `postcss@8.4.31` and `postcss-selector-parser@6.1.5` transitively, both below their patched versions. The compatible remediation on this line is an npm `overrides` entry pinning `postcss` to `^8.5.23` and `postcss-selector-parser` to `^7.1.7`. This was applied and verified: the production CSS bundle is byte-identical before and after the override, and the web lint, typecheck, test, and build checks pass on the result. The remaining `npm audit` findings are development-tooling transitive dependencies only:

- `sprintf-js` (moderate, denial of service through unbounded precision specifiers) — the published latest version `1.1.3` is itself within the affected range, so no upstream fix exists.
- `braces` (high, stack exhaustion through deeply nested patterns) — the published latest version `3.0.3` is itself within the affected range, so no upstream fix exists.

Both are reached only through the Jest and file-watcher development toolchain and are not part of the shipped production dependency tree. They remain recorded as development-only debt with no available upstream remediation, and are not a production blocker. The remaining `eslint-config-next` and `tailwindcss` findings require the Next 16 and Tailwind 4 major migrations, which are outside the scope of this framework upgrade.

The final NuGet scan reports zero vulnerable packages in all eight desktop projects. `flutter pub outdated` does not provide or report a security advisory; it identifies discontinued transitive development packages (`build_resolvers`, `build_runner_core`, `js`, and `flutter_secure_storage_macos`) and major-version updates, none changed blindly.

## Gaps and next implementation work

Authentication endpoints, password reset, final rate-limit policy, roles/permissions, policies, device registration/revocation, offline database encryption decision, upload controls, durable audit trails, CSP/header rollout, explicit production CORS origin configuration, and PostgreSQL integration security tests remain future work. Security headers are **NOT IMPLEMENTED** (CSP, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, and frame protections); a tested rollout is required. CodeQL and Dependabot are configured locally; secret scanning, push protection, and private vulnerability reporting require repository administrator enablement and are **DOCUMENTED — NOT APPLIED**.

Email verification and multi-factor authentication are now implemented. Email verification gates writes through `EMAIL_NOT_VERIFIED`. Multi-factor authentication uses an authenticator-application one-time password enforced at credential issuance, with single-use recovery codes, encrypted secret storage, replay protection, per-challenge lockout, and single-use challenges. See [ADR 0032](../adr/0032-multi-factor-authentication.md).
