# ADR 0032: Multi-Factor Authentication with Authenticator Applications

Status: ACCEPTED
Date: 2026-10-20

## Context

flowOS authenticates browser sessions through Laravel Sanctum cookies and mobile and desktop
clients through Sanctum personal access tokens. Both flows currently depend on a single factor:
the account password. For a business operating system that holds organization membership,
authorization roles, and financial records, password-only authentication leaves the platform
dependent on password strength and on the absence of credential-phishing.

The platform is designed initially for Nigerian businesses. That constrains the choice of second
factor: per-message costs, mobile network reliability, handset coverage, and SIM-swap exposure all
weigh against the security benefit of each candidate factor.

Multi-factor authentication also has to work for three different clients. The browser client has
a cookie session, the mobile client has a device with a camera, and the desktop client has a
native application. The factor must be enforceable at the point where a credential is issued, not
only inside one client.

## Decision

Multi-factor authentication uses a time-based one-time password (TOTP, RFC 6238) generated by an
authenticator application, with single-use recovery codes as the fallback.

### Factor selection

TOTP with an authenticator application is adopted as the primary second factor.

- **SMS one-time passwords** are rejected. Per-message cost and delivery reliability are poor in
  the target market, and SMS is vulnerable to SIM-swap and carrier interception, so it would add
  availability risk without a proportional security gain.
- **Email one-time passwords** are rejected. An emailed code is readable by whoever controls the
  mailbox, which is exactly the account an attacker who already phished the password would try to
  take over. Email is already used for verification and password reset; it is not a second factor.
- **WebAuthn / FIDO2 passkeys** are deferred, not rejected. It is the strongest option and is the
  planned successor once the mobile and desktop clients can register platform authenticators. It
  requires device registration and a browser capability that the current clients do not expose, so
  it cannot be the first factor implemented.

### Enforcement point

The second factor is enforced where a credential is issued, not on every API request. A successful
password check for an account with multi-factor authentication enrolled does **not** issue a
session or a personal access token. The server instead issues a short-lived, single-use
authentication challenge. The client exchanges that challenge and a second factor for the real
credential.

This boundary is deliberate. A stolen password alone produces an unusable challenge rather than an
API credential, so no partially-trusted credential ever exists, and there is no per-request
multi-factor state to carry through the token and session middleware.

Both the session route and the token route are covered. A challenge issued for one purpose cannot
be redeemed for the other, and a challenge cannot be redeemed twice.

### Replay, lockout, and recovery

- **Replay.** The server records the last accepted time-step counter per account. A code at or
  below that counter is rejected, so a code cannot be replayed inside its own validity window.
- **Lockout.** A challenge permits a bounded number of failed verification attempts. Once the
  bound is reached the challenge is consumed and the client must authenticate again with the
  password. Failed attempts are also rate limited at the endpoint.
- **Recovery.** Enrollment returns a fixed set of single-use recovery codes, shown exactly once.
  They are stored hashed, and each accepted recovery code is removed. Recovery is only a fallback:
  it does not re-enrol the account, and a user who exhausts recovery codes must re-enrol with the
  authenticator application.

### Secret handling

The shared secret is encrypted at rest with the application key, recovery codes are hashed, and
the pending secret used during enrolment is discarded if enrolment is not confirmed.

### Implementation

TOTP is implemented in the application against RFC 6238 using the PHP standard library
(`hash_hmac`), rather than by adding a third-party authentication package. The implementation is
verified against the RFC 6238 test vectors so that correctness is demonstrated rather than
assumed. Adding a dependency was evaluated and rejected because the required primitives are in the
standard library and the algorithm is fully specified.

## Alternatives Considered

- Ship without multi-factor authentication: rejected. The platform stores financial and
  authorization data and already treats dependency and tenancy correctness as release blockers.
- Enforce the second factor on every request using a claim on the credential: rejected. It
  requires the credential itself to carry an unverified state, which means an API credential
  exists before the second factor is satisfied, and it multiplies the state that middleware and
  token validation must reason about.
- Use SMS one-time passwords: rejected for cost, reliability, and SIM-swap exposure in the target
  market.
- Use email one-time passwords: rejected because it does not resist the phishing attack it is
  meant to mitigate.
- Use WebAuthn as the first factor: deferred until the mobile and desktop clients can register
  platform authenticators.
- Add a third-party TOTP package: rejected. The algorithm is fully specified, the required
  primitives are in the PHP standard library, and the dependency would carry its own supply-chain
  and advisory surface for no capability the platform does not already have.

## Consequences

### Positive

- A stolen password alone cannot obtain an API credential.
- The second factor is available to every client without hardware requirements or per-message
  cost.
- Replay, lockout, and single-use challenges are enforced server-side, so a client cannot bypass
  them by changing its request.
- No new runtime dependency is introduced.

### Negative / Trade-offs

- Clients must implement a challenge exchange, which is new protocol surface for the web, mobile,
  and desktop clients.
- Users can lose access if they lose both the device and the recovery codes. The recovery path is
  therefore the only supported way back in, and it is deliberately narrow.
- TOTP codes depend on device clock accuracy, so a bounded verification window is required.
- Recovery codes are shown once and must be stored by the user.

## Security / Tenancy Impact

Multi-factor authentication establishes platform identity only. It does not establish tenant
context and does not grant organization access: membership remains the authorization relationship
and the active membership check remains the tenant gate. A second factor never substitutes for
membership.

Challenges are bound to one account and one purpose, expire quickly, and are consumed on first
use, including on a failed verification that exhausts the attempt bound.

## Offline / Data Impact

No offline client can complete a challenge exchange without connectivity, because the challenge is
server state and the time-based code requires the server to validate a counter. The offline client
story therefore needs a separate decision for how a queued multi-factor enrolment or recovery
works without a server. This does not change the offline model recorded in ADR 0012, and no offline
multi-factor behaviour is claimed here.
